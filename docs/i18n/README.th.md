# repo-radar

> โครงการ 365 Open Source #027 · แดชบอร์ดในเครื่องที่คอยเฝ้าดู Git repo ทั้งหมดของคุณ และบอกให้รู้ว่าอันไหนต้องการให้คุณจัดการ

คุณมี Git repo เยอะเกินกว่าจะไล่ตามไหวด้วยตัวเอง repo-radar คอยเฝ้าดูให้ทั้งหมด แล้วหยิบเฉพาะไม่กี่อันที่ต้องให้คุณจัดการตอนนี้ขึ้นมาให้ — ส่วนที่เหลือจะได้ไม่ต้องมาคอยพะวง

มันช่วยเปิดให้เห็นสิ่งที่ปกติคุณมักลืมไปตรวจ:

- **repo ที่คุณลืมไปแล้ว** — ทุก repo ที่คุณเป็นเจ้าของอยู่บนหน้าจอเดียว ค้นหาได้ เปิดอันไหนก็ได้ด้วยคลิกเดียว
- **งานที่ยังทำค้างไว้** — การเปลี่ยนแปลงที่ยังไม่ commit ยังไม่ push หรือ stash ไว้ ถูกทำเครื่องหมายเตือนไว้ก่อนที่มันจะหลุดมือคุณไป
- **GitHub กำลังรอคุณอยู่** — PR ที่เปิดค้าง, issue และ CI ที่ล้มเหลวจากทุก repo รวบรวมผ่าน `gh` ที่ล็อกอินอยู่แล้วในเครื่องของคุณ
- **โปรเจกต์ที่กำลังจะร้างไป** — อันที่คุณไม่ได้แตะมานานเกินไป หรือเลยกำหนดที่ควรปล่อยรุ่น

อันที่ต้องลงมือจัดการจะถูกดันขึ้นไปไว้บนสุดของบอร์ดเป็นคิว เรียงตามความเร่งด่วน หนึ่งรายการต่อหนึ่ง repo — คลิกแล้วจัดการได้ทันที กด ✓ เพื่อเคลียร์ทิ้ง แล้วมันจะไม่โผล่มาอีกจนกว่าจะมีอะไรเปลี่ยนแปลงจริง ๆ และเมื่อไม่มีอะไรค้างอยู่ มันจะขึ้นว่า "all clear" ส่วน repo ที่เหลือ แค่ค้นหาก็เรียกดูได้เสมอ

## การติดตั้ง

ดาวน์โหลดไฟล์สำหรับแพลตฟอร์มของคุณจาก [Releases](https://github.com/rockbenben/repo-radar/releases) — ไม่ต้องมี Node.js เนื่องจากแอปยังไม่ได้เซ็นโค้ด แต่ละระบบปฏิบัติการจึงขึ้นเตือนตอนเปิดครั้งแรก:

- **Windows** — รัน `repo-radar-<version>-x64-setup.exe`; ที่หน้าต่าง SmartScreen ให้คลิก *More info → Run anyway*
- **macOS** — เปิด `repo-radar-<version>-arm64.dmg` แล้วลากแอปไปไว้ใน Applications ครั้งแรกให้คลิกขวา → Open หาก macOS บอกว่าแอปเสียหาย ให้ล้างค่า quarantine flag สักครั้งด้วย `xattr -cr /Applications/repo-radar.app`
- **Linux** — `chmod +x repo-radar-<version>-x86_64.AppImage && ./repo-radar-<version>-x86_64.AppImage`

หรือรันจากซอร์สโค้ด:

```bash
npm install
npm start
```

เมื่อเปิดครั้งแรก ให้คลิก **เพิ่มไดเรกทอรีที่จะสแกน** (หรือ ⚙ ตั้งค่า → ไดเรกทอรีที่จะสแกน) แล้วชี้ไปยังโฟลเดอร์ที่เก็บ repo ของคุณ — ไม่ต้องยุ่งกับ JSON ไม่ต้องรีสตาร์ท พอกดบันทึกมันก็สแกนใหม่ให้ทันที ส่วนการตั้งค่าเก็บอยู่ที่ `~/.repo-radar/config.json` เผื่อคุณอยากแก้เอง

## บอร์ด

หนึ่งการ์ดต่อหนึ่ง repo — สีสถานะสุขภาพ, branch, สรุป working tree, ahead/behind, คอมมิตล่าสุด, แท็ก — พร้อมปุ่มคลิกเดียว **editor / terminal / folder** บนทุกการ์ด จากตรงนี้คุณสามารถ:

- **ค้นหา** — ค้นหา, คลิกภาษา / `#tag` / ไฟแจ้งเตือนเพื่อกรอง, เรียงลำดับ และจัดกลุ่มตามโฟลเดอร์หรือภาษา; บันทึกการกรอง + เรียงลำดับ + จัดกลุ่มใด ๆ เป็น view ที่ตั้งชื่อได้ ⌘/Ctrl-K เปิดตัวเปิดโปรแกรมด่วน
- **ทำงานเป็นชุด** — เลือก repo เพื่อ fetch / pull (`--ff-only`) / push หรือสั่งรันคำสั่ง shell พร้อมกันทีเดียวทั่วทุกอัน (มีตัวอย่างแบบ dry-run ให้ดูก่อน และแยกผลลัพธ์ราย repo) ถ้า repo ใดล้มเหลว ก็ไม่ทำให้ที่เหลือสะดุดตาม
- **เจาะลึกเข้าไปใน repo** — แผงรายละเอียดให้สรุปสถานะสุขภาพแบบเต็ม, สลับ / สร้าง / ทิ้ง branch, **commit ในที่เดิม** พร้อม diff แบบเรียลไทม์, GitHub PR & CI ตามต้องการ, คอมมิตล่าสุด, stash, heatmap 12 สัปดาห์ และการล้าง branch ที่ merge แล้วแบบคลิกเดียว — ซึ่งจะเสนอให้เฉพาะเมื่อคุณอยู่บน `main`/`master` เพราะนั่นเป็นตำแหน่งเดียวที่ «merge แล้ว» หมายถึง merge เข้าสายหลักจริง ๆ การทิ้งการเปลี่ยนแปลงจะคืนค่าไฟล์ที่ติดตามอยู่และลบไฟล์ที่ไม่ได้ติดตาม แต่จะไม่แตะเนื้อหาใน submodule และ git repository ที่ซ้อนอยู่แบบไม่ได้ติดตาม หากยังมีอะไรเหลืออยู่ มันจะบอกคุณตรง ๆ แทนที่จะรายงานว่าสำเร็จ
- **อัปเดตอยู่เสมอ** — เส้นทางรีเฟรชโดยค่าเริ่มต้นคือการสแกนซ้ำทุก 30 นาที บวกกับการสแกนเองจากแถบด้านบน ส่วน auto-scan แบบเฝ้าดูไฟล์นั้น **ปิดไว้โดยค่าเริ่มต้น** และเปิดเองได้ในแผงตั้งค่า มันทำงานในเครื่องล้วนและไม่แตะเครือข่ายเลย แต่เมื่อมีหลายโปรเจกต์กำลังบิลด์พร้อมกัน บัฟเฟอร์แจ้งเตือนของเคอร์เนลจะล้นอยู่ตลอด และการล้นแต่ละครั้งมีราคาเท่ากับการสแกนซ้ำหนึ่งรอบ — แพงเกินไปสำหรับเครื่องมือที่มีไว้ «ชำเลืองดูว่ามีอะไรเปลี่ยน» เมื่อเปิดใช้แล้ว บน Windows และ macOS ใช้ตัวเฝ้าดูแบบเรียกซ้ำเพียงตัวเดียวต่อหนึ่งไดเรกทอรีที่สแกน ก็ครอบคลุม repo ทั้งหมดที่อยู่ข้างใต้ ดังนั้นการเพิ่ม ลบ หรือเปลี่ยนชื่อ repo จะปรากฏภายในไม่กี่วินาที ส่วนบน Linux จะเฝ้าดู repo แยกทีละตัว และ `watchLimit` (ค่าเริ่มต้น 200, 0 = ไม่จำกัด) จำกัดจำนวนที่เฝ้าดู โดยให้ลำดับความสำคัญกับรายการโปรดและอันที่คอมมิตล่าสุด หากล้นต่อเนื่อง การสแกนซ้ำที่ตามเก็บจะถ่างระยะแบบทวีคูณ (อย่างมากทุก 30 นาที) และไม่สร้างตัวเฝ้าดูขึ้นใหม่อีกต่อไป — จะสร้างใหม่เฉพาะตอนที่เป้าหมายการเฝ้าดูหายไปจริง ๆ การสแกนซ้ำทุก 30 นาทีคอยเก็บตกสิ่งที่ตัวเฝ้าดูพลาดไป แถบด้านบนแสดง «สแกนล่าสุด» และแผงตั้งค่าแสดงความครอบคลุมแบบเรียลไทม์ «เฝ้าดู M จาก N» การเปลี่ยนชื่อหรือย้าย repo ยังคงรักษาแท็ก ดาว สถานะเก็บเข้าคลัง และบันทึกย่อของมันไว้ — repo-radar ติดตามตัวตนของ repo ไม่ใช่แค่พาธ การจับคู่จะเกิดขึ้นในรอบสแกน **ถัดจากการย้ายทันที** จึงเหลือช่องว่างสองแบบ แบบแรกคือการย้ายข้ามไดรฟ์ที่ช้าจนคร่อมสองรอบสแกน และมีการเพิ่ม/ลบ repo อื่นหรือการสแกนซ้ำตามรอบมาแทรกกลาง แบบที่สองคือปลายทางของการย้ายไม่ถูกสแกนในรอบนั้น — การย้าย repo ออกไปนอกไดเรกทอรีที่สแกน แล้วเพิ่งเพิ่มตำแหน่งใหม่เข้าเป็นไดเรกทอรีที่สแกนในภายหลัง เป็นทางที่พบบ่อยที่สุดที่จะเจอกรณีนี้ ทั้งสองแบบจะถอยไปใช้การระบุตัวตนตามพาธ: repo กลับมาเป็นการ์ดใหม่ ส่วนแท็ก/ดาว/คลัง/บันทึกย่อ ยังค้างอยู่ใต้ id ที่มันไม่ได้ถืออีกแล้ว ส่วน fetch เบื้องหลังตามกำหนดเวลาต้องเปิดเอง มีแท็บ **Stats** (heatmap คอมมิตตลอดทั้งปี, ใช้งานมาก/น้อยที่สุด) และแท็บ **Worklog** ที่คัดลอกช่วงวันที่เป็นรายงานประจำสัปดาห์แบบ Markdown
- **เริ่มและย้าย repo** — **+ New** แนะนำโปรเจกต์เลขลำดับถัดไป, รัน `git init`, เขียน README และรับเข้าสู่บอร์ด; การส่งออก / นำเข้า manifest พาการตั้งค่าของคุณข้ามเครื่องได้

UI คือ antd 6 ในธีมห้องนักบิน (instrument-cockpit) แบบเข้ม แปลเป็น 18 ภาษา (จับคู่กับเบราว์เซอร์ของคุณโดยอัตโนมัติในการเข้าครั้งแรก, RTL สำหรับภาษาอาหรับ)

## ทำงานเงียบ ๆ อยู่เบื้องหลัง

การปิดหน้าต่างจะเป็นการย่อ repo-radar ลงไปพักที่ถาดระบบ (tray) โดยที่การสแกนซ้ำตามเวลา การเฝ้าดูไฟล์ (ถ้าเปิดไว้) การ fetch ตามกำหนดเวลา และการแจ้งเตือนจาก GitHub ยังทำงานต่อไป — คลิกไอคอนที่ถาดระบบเพื่อเรียกบอร์ดกลับมา หรือถ้าจะปิดจริง ๆ ก็สั่งออกจากเมนูของถาดระบบ (บน Linux ที่ถาดระบบบนเดสก์ท็อปมักไว้ใจไม่ค่อยได้ การปิดหน้าต่างจะกลายเป็นการออกไปเลย ให้เปิด เริ่มเมื่อเข้าสู่ระบบ ไว้แทน เพื่อให้มันเปิดค้างทำงานอยู่ตลอด)

เมื่อออกจากโปรแกรม repo-radar จะรองานของ git ที่กำลังทำอยู่ให้เสร็จ — pull แบบชุด, การทิ้ง stash, fetch ตามกำหนดเวลา — นานที่สุด 10 วินาที เพื่อไม่ให้มีอะไรถูกตัดกลางคันระหว่างเขียนแล้วทิ้ง `.git/index.lock` ที่ค้างไว้ ถ้าเวลานั้นไม่พอ มันก็จะออกอยู่ดีและบันทึกเรื่องนี้ลงใน log ซึ่งเป็นที่เดียวที่จะอธิบาย `index.lock` ที่คุณไปเจอในภายหลัง

เปิด **เริ่มเมื่อเข้าสู่ระบบ** ใน ⚙ ตั้งค่า แล้วมันจะเริ่มแบบไม่มีหน้าต่างพร้อมกับเซสชันของคุณ — ไม่มีหน้าต่างจนกว่าคุณจะเรียก การแจ้งเตือนบนเดสก์ท็อปที่เป็นตัวเลือกเสริมจะทำงานเฉพาะเมื่อมีอะไร *ใหม่* เข้าสู่คิวของคุณเท่านั้น แม้ปิดหน้าต่างอยู่ การอัปเกรดออกแบบให้ทำเองโดยตั้งใจ (ไม่มีอัปเดตอัตโนมัติ): แค่รันตัวติดตั้งใหม่ทับตัวเก่า ส่วนไฟล์ Log จะถูกเก็บไว้ที่ `<config dir>/logs/repo-radar.log`

## การกำหนดค่า

ทุกอย่างที่ UI แตะต้องจะถูกบันทึกไปที่ `~/.repo-radar/config.json` — คุณแทบไม่ต้องเปิดมันเลย ฟิลด์ที่สำคัญ:

| ฟิลด์ | หน้าที่ |
| --- | --- |
| `roots` / `excludes` / `manualRepos` | ที่ที่จะสแกน (ค้นหา `.git` ลึกได้ถึง 6 ชั้น และไม่เดินตาม symlink), อะไรที่จะข้าม และ repo ที่เพิ่มนอกเหนือ roots — รายการใน `manualRepos` ที่ถูกเปลี่ยนชื่อหรือย้ายจะไม่ถูกติดตามด้วยตัวตนเหมือน repo ที่สแกนเจอ การ์ดจะขึ้นสถานะผิดพลาดจนกว่าคุณจะมาอัปเดตพาธที่นี่ และถ้าการย้ายเกิดขึ้นนานกว่าหนึ่งรอบสแกน การอัปเดตนั้นจะเรียกการ์ดกลับมาได้ แต่ไม่ได้เรียกแท็ก/ดาว/คลัง/บันทึกย่อกลับมาด้วย |
| `health` | `{ staleDays, disabledRules }` — ปรับเกณฑ์ "stale" หรือปิดการตรวจสอบแต่ละอย่าง |
| `open` | เทมเพลตคำสั่งสำหรับปุ่ม editor / terminal / folder (`{path}` = path ของ repo) |
| `autoWatch` / `autoScanMinutes` / `watchLimit` / `autoFetchMinutes` / `notifications` | พฤติกรรมเบื้องหลัง — ค่าเริ่มต้นเปิดไว้เฉพาะ `autoScanMinutes` (30) ส่วนอีกสามตัวรวมทั้ง `autoWatch` ปิดไว้ ส่วน `watchLimit` (200, 0 = ไม่จำกัด) **มีผลบน Linux เท่านั้น** ซึ่งเป็นที่ที่ repo ถูกเฝ้าดูแยกทีละตัว ขณะที่ Windows และ macOS ใช้ตัวเฝ้าดูแบบเรียกซ้ำหนึ่งตัวต่อไดเรกทอรีที่สแกน และครอบคลุม repo ทั้งหมดเสมอ |
| `tags` / `favorites` / `groupOverrides` / `notes` / `archived` | การจัดระเบียบราย repo |

ข้าง ๆ `config.json` ยังมีอีกสองไฟล์ ซึ่งลบได้อย่างปลอดภัยทั้งคู่ — repo-radar จะสร้างขึ้นใหม่ เพียงแต่ราคาที่จ่ายต่างกัน `repo-cache.json` จำฟิลด์ git ที่ «หนัก» ของแต่ละ repo (stash, แท็ก, remote, branch ที่ merge แล้ว…) โดยผูกกับลายนิ้วมือของ `.git` ทำให้ repo ที่ไม่มีอะไรเปลี่ยนข้ามการเรียก git เหล่านั้นได้ในการสแกนรอบถัดไป ลบมันไปก็เพียงทำให้การสแกนรอบถัดไปช้าลงหนึ่งครั้ง ส่วน `repo-identity.json` คือสมุดทะเบียนตัวตน ที่ทำให้ repo ซึ่งถูกเปลี่ยนชื่อหรือย้ายยังรักษาแท็ก ดาว สถานะเก็บเข้าคลัง และบันทึกย่อไว้ได้ แทนที่จะถูกมองว่าเป็น repo ใหม่ทั้งหมด ไฟล์นี้ถ้าหายไป ความเสียหายเกิดทันทีไม่ใช่ทีหลัง: repo ใดที่ถูกเปลี่ยนชื่อหรือย้ายไป **ก่อน** ที่ไฟล์จะหาย จะได้ id ใหม่ทั้งหมดในการสแกนครั้งถัดไปเลย และแท็ก/ดาว/คลัง/บันทึกย่อของมันจะค้างอยู่ใต้ id ที่มันไม่ได้ถืออีกแล้ว repo ที่ไม่เคยถูกเปลี่ยนชื่อจะไม่ได้รับผลกระทบ และตั้งแต่สมุดทะเบียนถูกสร้างขึ้นใหม่ การเปลี่ยนชื่อจากนั้นไปก็ได้รับการคุ้มครองอีกครั้ง

`REPO_RADAR_CONFIG` และ `REPO_RADAR_PORT` (ค่าเริ่มต้น 17420) ใช้แทนที่ path ของ config และพอร์ต — ตั้งค่า **ทั้งสองตัว** เพื่อรันอินสแตนซ์ที่สองที่เป็นอิสระอย่างสมบูรณ์ เซิร์ฟเวอร์ผูกกับ `127.0.0.1` เท่านั้น และตรวจสอบ header Origin ในทุกคำขอ API และ WebSocket

พอร์ตเริ่มต้นถูกวางไว้เหนือช่วงพอร์ตไดนามิกของระบบโดยตั้งใจ: โดยค่าเริ่มต้น Windows ใช้ 49152–65535 แต่จะกลายเป็น 1024–15000 เมื่อติดตั้ง Hyper-V/WSL2 และระบบจะจองพอร์ตเป็นบล็อกทั้งก้อนจากช่วงที่กำลังใช้งานอยู่ — พอร์ตที่อยู่ในนั้นจะ bind ไม่สำเร็จด้วย `EACCES` และบล็อกเหล่านี้ยังเลื่อนไปมาทุกครั้งที่รีบูต

หาก bind พอร์ต**เริ่มต้น**ไม่ได้จริง ๆ repo-radar จะเปลี่ยนไปใช้ตัวเลือกถัดไป (`+1000`, `+2000`, `+3000` แล้วจึงให้ระบบกำหนดให้) แทนที่จะไม่ยอมเริ่มทำงาน จากนั้นจะจดจำพอร์ตที่ลงเอยและใช้พอร์ตเดิมในการเปิดครั้งถัดไป พร้อมแสดงไว้ข้างหมายเลขเวอร์ชันใน ⚙ การตั้งค่า การจดจำสำคัญเพราะพอร์ตเป็นส่วนหนึ่งของ origin ของหน้า และบอร์ดเก็บมุมมองที่บันทึกไว้ บันทึกกิจกรรม ธีม และภาษา ไว้ในที่เก็บของเบราว์เซอร์ซึ่งผูกกับ origin — ถ้าปล่อยให้พอร์ตสลับไปมา ข้อมูลเหล่านั้นจะเหมือนหายไปแล้วกลับมา ลบ `<โฟลเดอร์คอนฟิก>/port-state.json` เพื่อกลับไปใช้พอร์ตเริ่มต้น

พอร์ตที่คุณกำหนดเองผ่าน `REPO_RADAR_PORT` จะไม่ถูกเปลี่ยนเด็ดขาด — มันคือคำสัญญาต่อบุ๊กมาร์ก อัปสตรีมของ reverse proxy และสคริปต์ของคุณ ดังนั้นถ้า bind ไม่ได้ก็จะล้มเหลวอย่างชัดเจน เช่นเดียวกับ `npm run dev` ที่เป้าหมายพร็อกซีของ vite ถูกกำหนดตายตั้งแต่ตอนโหลดคอนฟิก

## การพัฒนา

```bash
npm run dev     # vite + หน้าต่างแอปพร้อม hot reload
npm test        # ชุดทดสอบ server + web + desktop และการตรวจ type
npm run dist    # build ตัวติดตั้งไปที่ dist-electron/
```

Stack: เชลล์ Electron + Node + Hono (การเข้าถึง git ทั้งหมดผ่าน `spawn`, ไม่มี native deps) + Vite / React 19 / antd 6, พร้อม chokidar + WebSocket สำหรับการอัปเดตแบบเรียลไทม์ เซิร์ฟเวอร์ Hono ทำงานอยู่ภายในโปรเซสหลักของ Electron และหน้าต่างจะโหลดผ่าน `127.0.0.1` ดังนั้น UI จึงเป็น HTTP + WebSocket ธรรมดา — เหมือนกับที่จะเป็นถ้ารันในเบราว์เซอร์ทุกประการ
