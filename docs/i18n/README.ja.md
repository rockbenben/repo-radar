# repo-radar

> すべてのGitリポジトリを見守り、どれにあなたの対応が必要かを知らせるローカルダッシュボード。

手作業で把握しきれないほど多くのGitリポジトリを抱えているはずです。repo-radar はそのすべてを見守り、今あなたの対応が必要な数件だけを示します——残りは頭の片隅から追い出してかまいません。

放っておけば確認を忘れてしまうものを、代わりに浮かび上がらせます。

- **見失ったリポジトリ** —— 所有するすべてのリポジトリが1画面に。検索でき、どれもワンクリックで開けます。
- **やり残した作業** —— 未コミット・未プッシュ・スタッシュされた変更を、失う前にフラグ表示します。
- **GitHubがあなたを待っている** —— すべてのリポジトリにまたがる、開いているPR・Issue・失敗したCIを、ローカルで既に認証済みの `gh` を通じて集約します。
- **停滞しているプロジェクト** —— 長らく手つかずのもの、あるいはリリースが遅れているもの。

対応が必要なものはキューとしてボード上部にせり上がり、緊急度でランク付けされ、1リポジトリにつき1項目——クリックすればそのまま対応できます。✓ で消せば、実際に何か変化が起きるまで消えたままになります。待っているものが何もなければ「all clear」と表示されます。残りのリポジトリはいつでも検索ひとつで見つかります。

## インストール

[Releases](https://github.com/rockbenben/repo-radar/releases) からお使いのプラットフォーム用ファイルを取得してください——Node.js は不要です。アプリはコード署名されていないため、各OSが初回実行時に警告を表示します。

- **Windows** —— `repo-radar-<version>-x64-setup.exe` を実行します。SmartScreen のプロンプトで *詳細情報 → 実行* をクリックしてください。
- **macOS** —— `repo-radar-<version>-arm64.dmg` を開き、アプリを Applications にドラッグします。初回は右クリック → 開くで。macOS が「壊れている」と言い張る場合は、`xattr -cr /Applications/repo-radar.app` で隔離属性を一度クリアしてください。
- **Linux** —— `chmod +x repo-radar-<version>-x86_64.AppImage && ./repo-radar-<version>-x86_64.AppImage`。

またはソースから実行：

```bash
npm install
npm start
```

初回起動時は、**スキャン対象を追加**（または ⚙ 設定 → スキャン対象ディレクトリ）をクリックし、リポジトリを置いているフォルダを指定してください——JSON も再起動も不要で、保存した瞬間に再スキャンされます。手で編集したい場合、設定は `~/.repo-radar/config.json` にあります。

## ボード

リポジトリごとに1枚のカード——ヘルス状態の色、ブランチ、作業ツリーの内訳、ahead/behind、最終コミット、タグ——すべてのカードにワンクリックの **エディタ / ターミナル / フォルダ** が付いています。ここから、次のことができます。

- **見つける** —— 検索し、言語 / `#tag` / Attentionランプをクリックして絞り込み、フォルダや言語で並び替え・グルーピングします。任意のフィルタ + 並び替え + グルーピングを名前付きビューとして保存できます。⌘/Ctrl-K でランチャーが開きます。
- **一括で操作する** —— リポジトリを選択して fetch / pull（`--ff-only`）/ push、あるいはそれらをまたいでシェルコマンドを並列実行できます（ドライラン・プレビューとリポジトリごとの出力付き）。1つのリポジトリが失敗しても他は止まりません。
- **リポジトリを掘り下げる** —— 詳細パネルでは、完全なヘルス内訳、ブランチの切り替え / 作成 / 破棄、ライブ差分付きの **その場でコミット**、オンデマンドのGitHub PR & CI、最近のコミット、スタッシュ、12週間のヒートマップ、そしてマージ済みブランチのワンクリック整理が行えます——この整理は `main`/`master` にいるときだけ提示されます。「マージ済み」が「トランクにマージ済み」と一致するのは、その位置に限られるからです。変更の破棄は追跡ファイルを復元し未追跡ファイルを削除しますが、サブモジュールの中身と未追跡のネストされた git リポジトリには触れません。破棄しきれなかったものがある場合は、成功と報告せずにそのことを伝えます。
- **最新に保つ** —— 既定の更新経路は30分ごとの定期再スキャンと、ツールバーからの手動再スキャンです。ファイル監視による自動スキャンは**既定でオフ**で、設定パネルから任意で有効にします。ローカルのみでネットワークは使いませんが、複数のプロジェクトが同時にビルドしているとカーネルの通知バッファが絶えずあふれ、あふれるたびに再スキャンを一度払うことになります——「何が変わったかを一目で見る」ための道具に、その常時コストは見合いません。有効にすると、Windows と macOS では、スキャンディレクトリごとに1つの再帰監視ハンドルでその配下のすべてのリポジトリをカバーするため、リポジトリの追加・削除・改名が数秒で反映されます。Linux ではリポジトリを個別に監視し、`watchLimit`（既定200、0 = 無制限）が監視数を制限して、お気に入りと最近コミットされたリポジトリを優先します。あふれが続く場合、穴埋めの再スキャンは指数的に間隔を空け（最長30分に1回）、監視ハンドルを作り直すこともしません——作り直すのは監視対象が実際に失われたときだけです。取りこぼしを補う30分ごとの定期再スキャン、ツールバーの「最終スキャン」表示、設定パネルの「N 件中 M 件を監視」というリアルタイムのカバレッジ表示もあります。リポジトリを改名・移動しても、タグ・スター・アーカイブ状態・メモは保持されます——repo-radar が追跡するのはパスではなくリポジトリのアイデンティティです。照合は移動の**直後のスキャン回**で行われるため、2つの隙間が残ります。1つは、ボリュームをまたぐ遅い移動が2つのスキャン回にまたがり、その間に別のリポジトリの追加・削除や定期再スキャンが挟まる場合。もう1つは、移動先がそのスキャン回でスキャンされない場合——リポジトリをスキャンディレクトリの外に移し、後からその新しい場所をスキャンディレクトリに追加するのが典型です。どちらもパスベースの識別にフォールバックし、リポジトリは新しいカードとして現れ、タグ/スター/アーカイブ/メモはもう持っていない id の下に取り残されます。スケジュール式のバックグラウンドフェッチは任意で有効化します。**Stats** タブ（年間コミットヒートマップ、最も/最も活発でない）と、日付範囲をMarkdown週次レポートとしてコピーする **Worklog** タブもあります。
- **リポジトリを新規作成・移行する** —— **+ New** は次の連番プロジェクトを提案し、`git init` を実行し、READMEを書き込み、ボードに取り込みます。マニフェストのエクスポート / インポートで、セットアップをマシン間で持ち運べます。

UIは antd 6 のダークな計器盤（インストゥルメント・コックピット）テーマで、18言語にローカライズされています（初回訪問時はブラウザに自動一致、アラビア語はRTL）。

## バックグラウンドで静かに動く

ウィンドウを閉じても repo-radar はトレイに収まり、定期再スキャン・ファイル監視（有効にしている場合）・定期フェッチ・GitHub 通知は動き続けます——トレイアイコンをクリックするとボードが戻り、完全に終了するにはトレイメニューから終了します。（デスクトップトレイが当てにならない Linux では、閉じる操作が終了になります。常駐させるには ログイン時に起動 を使ってください。）

終了時は、すでに実行中の git 処理——一括 pull、スタッシュの破棄、定期フェッチ——の完了を最大10秒待ちます。書き込みの途中で中断されて古い `.git/index.lock` が残らないようにするためです。待ち切れない場合はそのまま終了し、その旨をログに記録します。後で `index.lock` に遭遇したとき、理由を説明してくれるのはその1行だけです。

⚙ 設定で **ログイン時に起動** をオンにすると、セッションとともにウィンドウなしで起動します——呼び出すまでウィンドウは出ません。任意のデスクトップ通知は、*新しい* ものがキューに届いたときだけ、ウィンドウを閉じていても発火します。アップグレードは意図的に手動です（自動更新なし）。新しいインストーラーを旧版の上から実行してください。ログは `<config dir>/logs/repo-radar.log` に出力されます。

## 設定

UIが触れるものはすべて `~/.repo-radar/config.json` に保存されます——開く必要はめったにありません。重要なフィールド：

| フィールド | 説明 |
| --- | --- |
| `roots` / `excludes` / `manualRepos` | どこをスキャンするか（深さ6まで `.git` を探す。シンボリックリンクは辿りません）、何をスキップするか、roots 外で追加したリポジトリ——`manualRepos` のエントリは改名・移動されてもスキャン対象のリポジトリのようにアイデンティティで追跡されないため、ここでパスを更新するまでカードはエラーのままです。移動から1スキャン回以上経ってから更新した場合、カードは戻りますがタグ/スター/アーカイブ/メモは戻りません |
| `health` | `{ staleDays, disabledRules }` —— 「stale」のしきい値を調整、または個別チェックを無効化 |
| `open` | エディタ / ターミナル / フォルダ ボタンのコマンドテンプレート（`{path}` = リポジトリのパス） |
| `autoWatch` / `autoScanMinutes` / `watchLimit` / `autoFetchMinutes` / `notifications` | バックグラウンド動作——既定でオンなのは `autoScanMinutes`（30分）だけで、`autoWatch` を含む他の3つはオフ。`watchLimit`（200、0 = 無制限）は **Linux でのみ適用**され、そこではリポジトリを個別に監視します。Windows と macOS はスキャンディレクトリごとに1つの再帰監視を使い、常にすべてのリポジトリをカバーします |
| `tags` / `favorites` / `groupOverrides` / `notes` / `archived` | リポジトリ単位の整理情報 |

`config.json` の隣にはもう2つファイルがあり、どちらも安全に削除できます——repo-radar が作り直しますが、コストは異なります。`repo-cache.json` は各リポジトリの「重い」git フィールド（スタッシュ、タグ、リモート、マージ済みブランチなど）を `.git` のフィンガープリントに紐づけて記憶しているので、変更のないリポジトリは次の再スキャンでそれらの git 呼び出しをスキップできます。削除しても、次の再スキャンが一度だけ遅くなるだけです。`repo-identity.json` はアイデンティティ台帳で、改名・移動されたリポジトリが新規リポジトリとして扱われる代わりにタグ・スター・アーカイブ状態・メモを保てるのはこれのおかげです。こちらの削除による損失は先送りではなく即時です。ファイルが失われる**前に**すでに改名・移動されていたリポジトリは、次のスキャンで新しい id を受け取り、そのタグ/スター/アーカイブ/メモはもう持っていない id の下に取り残されます。改名されたことのないリポジトリは影響を受けず、台帳が再構築されれば、それ以降の改名は再び保護されます。

`REPO_RADAR_CONFIG` と `REPO_RADAR_PORT`（既定 17420）は設定パスとポートを上書きします——**両方**を設定すれば、独立した2つ目のインスタンスを動かせます。サーバーは `127.0.0.1` にのみバインドし、すべてのAPIとWebSocketリクエストでOriginヘッダーを検証します。

既定ポートは意図的に OS の動的ポート範囲より上に置いています。Windows の既定は 49152–65535 ですが、Hyper-V/WSL2 を入れると 1024–15000 になり、システムは有効な範囲からブロック単位でポートを予約します——その中のポートは `EACCES` でバインドに失敗し、しかも予約区間は再起動のたびに動きます。

**既定**ポートがどうしてもバインドできない場合、repo-radar は起動を諦めるのではなく次の候補（`+1000`、`+2000`、`+3000`、最後は OS 任せ）へ切り替え、落ち着いたポートを記憶して次回以降も同じものを使い、⚙ 設定のバージョン欄の隣に表示します。記憶するのが重要なのは、ポートがページの origin の一部だからです——保存したビュー、アクティビティログ、テーマ、言語は origin 単位のブラウザストレージに入っているため、ポートが行ったり来たりするとそれらが消えたり戻ったりして見えます。既定ポートに戻すには `<設定ディレクトリ>/port-state.json` を削除してください。

`REPO_RADAR_PORT` で自分が指定したポートは決して差し替えられません——ブックマーク、リバースプロキシの上流、スクリプトに対する約束だからです。バインドできなければはっきり失敗します。`npm run dev` も同様で、vite のプロキシ先は設定読み込み時に固定されます。

## 開発

```bash
npm run dev     # vite + ホットリロード対応のアプリウィンドウ
npm test        # server + web + desktop のテスト一式と型チェック
npm run dist    # インストーラを dist-electron/ にビルド
```

スタック：Electron シェル + Node + Hono（すべての git は `spawn` 経由、ネイティブ依存ゼロ）+ Vite / React 19 / antd 6、ライブ更新には chokidar + WebSocket。Hono サーバーは Electron のメインプロセス内で動作し、ウィンドウは `127.0.0.1` 経由で読み込むため、UI は普通の HTTP + WebSocket——ブラウザで動かす場合とまったく同じです。
