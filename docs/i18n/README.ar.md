# repo-radar

> خطة 365 مفتوح المصدر #027 · لوحة تحكم محلية تراقب كل مستودعات Git لديك وتُظهر لك أيها يحتاج انتباهك.

عدد مستودعات Git لديك أكبر من أن تتابعها يدوياً. يراقب repo-radar جميعها ويعرض لك القِلّة التي تحتاج إليك الآن — فيُريح ذهنك من الباقي.

يكشف لك ما كنت ستنسى التحقق منه لولاه:

- **مستودعات غابت عنك** — كل مستودع تملكه في شاشة واحدة، مع بحث، وتفتح أياً منها بنقرة واحدة.
- **عمل لم يكتمل** — تغييرات لم تُعمَل لها commit، أو لم تُدفَع بـ push، أو محفوظة في stash — تُعلَّم قبل أن تضيع منك.
- **GitHub بانتظارك** — طلبات دمج (PR) مفتوحة، ومشكلات (issues)، وحالات فشل في CI في كل مستودع، تُجمَع عبر أداة `gh` المحلية التي سبق أن سجّلت دخولك بها.
- **مشاريع بدأت تركد** — تلك التي لم تلمسها منذ وقت طويل، أو فات موعد إصدارها.

أما تلك التي تحتاج إلى إجراء فترتفع إلى أعلى اللوحة على هيئة قائمة انتظار، مرتّبة حسب درجة الإلحاح، عنصر واحد لكل مستودع — انقر عليه لتتصرّف حياله مباشرة. تجاهله بالضغط على ✓ فيبقى مختفياً إلى أن يتغيّر شيء فعلاً؛ وحين لا شيء بالانتظار تظهر عبارة "all clear". وتبقى بقية مستودعاتك على بُعد بحثٍ واحد دائماً.

## التثبيت

نزّل ملف منصّتك من [Releases](https://github.com/rockbenben/repo-radar/releases) — دون حاجة إلى Node.js. التطبيق غير موقَّع رقمياً، لذا يُصدر كل نظام تشغيل تحذيراً عند أول تشغيل:

- **Windows** — شغّل `repo-radar-<version>-x64-setup.exe`؛ عند ظهور تنبيه SmartScreen اضغط *More info → Run anyway*.
- **macOS** — افتح `repo-radar-<version>-arm64.dmg` واسحب التطبيق إلى Applications. انقر بزر الفأرة الأيمن → Open في المرة الأولى؛ وإذا وصفه macOS بأنه تالف، فامسح علامة الحجر الصحي مرة واحدة بـ `xattr -cr /Applications/repo-radar.app`.
- **Linux** — `chmod +x repo-radar-<version>-x86_64.AppImage && ./repo-radar-<version>-x86_64.AppImage`.

أو شغّله من المصدر:

```bash
npm install
npm start
```

عند التشغيل الأول، انقر على **إضافة مجلدات الفحص** (أو ⚙ الإعدادات → مجلدات الفحص) ووجّهه إلى المجلدات التي تحوي مستودعاتك — بلا JSON وبلا إعادة تشغيل؛ يعيد الفحص فور الحفظ. تبقى الإعدادات في `~/.repo-radar/config.json` إن كنت تفضّل تحريرها يدوياً.

## اللوحة

بطاقة واحدة لكل مستودع — لون الحالة الصحية، والفرع، وتفصيل شجرة العمل، ومقدار التقدّم/التأخّر عن الأصل، وآخر commit، والوسوم — مع أزرار **المحرر / الطرفية / المجلد** بنقرة واحدة على كل بطاقة. من هنا يمكنك:

- **البحث** — ابحث، وانقر على لغة / `#tag` / مصباح تنبيه للتصفية والفرز والتجميع حسب المجلد أو اللغة؛ احفظ أي تصفية + فرز + تجميع كعرض (view) مسمّى. والاختصار ⌘/Ctrl-K يفتح مُشغّلاً سريعاً (launcher).
- **التصرّف بالدفعات** — حدّد مستودعات لعمل fetch / pull (`--ff-only`) / push، أو نفّذ أمر Shell بالتوازي عليها جميعاً (مع معاينة تجريبية dry-run ومخرجات مستقلة لكل مستودع). وفشل مستودع واحد لا يوقف البقية أبداً.
- **التعمّق في مستودع** — تقدّم لوحة التفاصيل تفصيلاً كاملاً للحالة الصحية، وتبديل الفروع وإنشاءها والتخلّص منها، و**عمل commit في مكانه** مع diff حيّ، وعرض PR وCI من GitHub عند الطلب، وأحدث الـ commits، والـ stashes، وخريطة حرارية لاثني عشر أسبوعاً، وتنظيفاً بنقرة واحدة للفروع المدموجة سلفاً — ولا يُعرض هذا التنظيف إلا وأنت على `main`/`master`، فهو الموضع الوحيد الذي يعني فيه «مدموج سلفاً» أنه مدموج في الفرع الرئيسي. والتخلّص من التغييرات يستعيد الملفات المتعقَّبة ويحذف غير المتعقَّبة، لكنه لا يمسّ محتوى الوحدات الفرعية (submodules) ولا مستودعات git المتداخلة غير المتعقَّبة؛ وإن تبقّى شيء فهو يخبرك بذلك بدلاً من الإبلاغ عن نجاح.
- **البقاء محدَّثاً** — مسار التحديث الافتراضي هو فحص كامل كل 30 دقيقة إلى جانب الفحص اليدوي من الشريط العلوي. أما الفحص التلقائي بمراقبة الملفات فهو **معطَّل افتراضياً** ويُفعَّل عند الحاجة من لوحة الإعدادات: فهو محلي بالكامل ولا يلمس الشبكة، لكن حين تُبنى عدة مشاريع في وقت واحد يفيض مخزن إشعارات النواة باستمرار، وكل فيضان يكلّف فحصاً كاملاً — ثمن دائم أعلى مما ينبغي لأداة غرضها إلقاء نظرة على ما تغيَّر. وعند تفعيله، على Windows وmacOS تكفي مراقبة تعاودية واحدة لكل مجلد فحص لتغطية جميع المستودعات تحته، فيظهر إضافة مستودع أو حذفه أو إعادة تسميته في ثوانٍ؛ وعلى Linux تُراقَب المستودعات فرداً فرداً ويحدّ `watchLimit` (200 افتراضياً، 0 = بلا حدّ) عددها، مع أولوية للمفضّلة والأحدث commit. وإذا تكرر الفيضان تتباعد عمليات الفحص التعويضية أُسّياً (مرة كل 30 دقيقة على الأكثر) ولم تعد تعيد بناء مقابض المراقبة — فذلك لا يحدث إلا حين يختفي هدف المراقبة فعلياً. ويلتقط فحص كامل كل 30 دقيقة ما تفوته المراقبة، ويظهر «آخر فحص» في الشريط العلوي، وتعرض لوحة الإعدادات التغطية لحظياً («تُراقَب M من N»). وإعادة تسمية مستودع أو نقله تحفظ وسومه ونجمته وحالة أرشفته وملاحظاته — فـ repo-radar يتعقّب الهوية لا المسار وحده. والمطابقة تحدث في دورة الفحص **التالية مباشرة** للنقل، وهذا يترك ثغرتين: نقل بطيء بين وحدات تخزين يمتدّ على دورتَي فحص، ويتخلّله إضافة/إزالة مستودع آخر أو الفحص الدوري؛ ونقل لا يُفحَص مقصده في تلك الدورة — وإخراج مستودع من مجلدات الفحص ثم إضافة موضعه الجديد كمجلد فحص لاحقاً هو الطريق المعتاد للوقوع فيها. وكلتاهما ترتدّان إلى الهوية بالمسار: يعود المستودع كبطاقة جديدة، وتبقى وسومه ونجمته وأرشفته وملاحظاته تحت المعرّف الذي لم يعد يحمله. أما الـfetch المجدوَل في الخلفية فتُفعِّله بنفسك. وهناك تبويب **Stats** (خريطة حرارية للـ commits على مدار عام، الأكثر/الأقل نشاطاً) وتبويب **Worklog** ينسخ نطاقاً زمنياً على هيئة تقرير أسبوعي بصيغة Markdown.
- **بدء المستودعات ونقلها** — يقترح **+ New** المشروع المرقّم التالي، ويشغّل `git init`، ويكتب ملف README، ويضمّه إلى اللوحة؛ ويَنقل تصديرُ/استيرادُ الـ manifest إعداداتِك بين الأجهزة.

الواجهة مبنية على antd 6 بتصميم داكن يحاكي غرفة قيادة الأجهزة (instrument-cockpit)، مترجمة إلى 18 لغة (تُطابَق تلقائياً مع متصفحك عند الزيارة الأولى، ومن اليمين لليسار (RTL) للعربية).

## يعمل بهدوء في الخلفية

إغلاق النافذة يُنزل repo-radar إلى شريط النظام (tray) بحيث يستمر الفحص الدوري ومراقبة الملفات (إن فعّلتها) وعمليات fetch المجدوَلة وتنبيهات GitHub في العمل — انقر على أيقونة الشريط لإعادة اللوحة إلى الظهور، أو اخرج فعلياً من قائمة الشريط. (على Linux، حيث لا يُعتمَد على أشرطة النظام لسطح المكتب، يؤدي الإغلاق إلى الخروج بدلاً من ذلك؛ استخدم التشغيل عند تسجيل الدخول لإبقائه مقيماً.)

وعند الخروج ينتظر repo-radar حتى 10 ثوانٍ ريثما ينتهي عمل git الجاري فعلاً — عملية pull جماعية، أو stash تم التخلّص منه، أو fetch مجدوَل — كي لا يُقطَع شيء في منتصف الكتابة فيترك `.git/index.lock` قديماً. وإن لم تكفِ هذه المدة فهو يخرج على أي حال ويسجّل ذلك في السجل: وهو الموضع الوحيد الذي يفسّر لك `index.lock` تجده لاحقاً.

فعّل **التشغيل عند تسجيل الدخول** في ⚙ الإعدادات ليبدأ دون واجهة مع جلستك — بلا نافذة حتى تطلبها. تُطلَق إشعارات سطح المكتب الاختيارية فقط عندما يصل شيء *جديد* إلى قائمتك، حتى والنافذة مغلقة. الترقيات يدوية بحكم التصميم (لا تحديث تلقائي): شغّل المثبِّت الجديد فوق القديم. تُكتب السجلات في `<config dir>/logs/repo-radar.log`.

## الإعدادات

كل ما تلمسه الواجهة يُحفَظ في `~/.repo-radar/config.json` — نادراً ما تحتاج إلى فتحه. الحقول المهمة:

| الحقل | ماذا يفعل |
| --- | --- |
| `roots` / `excludes` / `manualRepos` | أين يفحص (يعثر على `.git` حتى عمق 6، دون تتبّع الروابط الرمزية)، وما الذي يتخطاه، والمستودعات المُضافة خارج الجذور — ومدخل `manualRepos` الذي يُعاد تسميته أو يُنقَل لا يُتعقَّب بالهوية كما يحدث لمستودع مفحوص؛ فتبقى بطاقته في حالة خطأ حتى تحدّث مساره هنا، وإذا مضى على النقل أكثر من دورة فحص واحدة فإن هذا التحديث يعيد البطاقة لا وسومها ونجمتها وأرشفتها وملاحظاتها |
| `health` | `{ staleDays, disabledRules }` — اضبط عتبة «الركود» أو عطّل فحوصاً فردية |
| `open` | قوالب أوامر لأزرار المحرر / الطرفية / المجلد (`{path}` = مسار المستودع) |
| `autoWatch` / `autoScanMinutes` / `watchLimit` / `autoFetchMinutes` / `notifications` | سلوك الخلفية — المفعَّل افتراضياً هو `autoScanMinutes` (30) وحده، والثلاثة الأخرى ومنها `autoWatch` معطَّلة. و`watchLimit` (200، 0 = بلا حدّ) **لا يُطبَّق إلا على Linux**، حيث تُراقَب المستودعات فرداً فرداً؛ أما Windows وmacOS فتستخدمان مراقبة تعاودية واحدة لكل مجلد فحص وتغطيان دائماً كل المستودعات |
| `tags` / `favorites` / `groupOverrides` / `notes` / `archived` | تنظيم لكل مستودع |

إلى جانب `config.json` يوجد ملفان آخران، وحذفهما آمن — فـ repo-radar يعيد بناءهما، لكن بتكلفتين مختلفتين. يحفظ `repo-cache.json` حقول git «الثقيلة» لكل مستودع (الـ stashes والوسوم والمستودعات البعيدة والفروع المدموجة…) مرتبطةً ببصمة `.git`، فيتخطّى المستودعُ غير المتغيّر تلك النداءات في الفحص التالي؛ وحذفه يجعل الفحص التالي أبطأ مرة واحدة فقط. و`repo-identity.json` هو سجلّ الهوية الذي يسمح لمستودع أُعيدت تسميته أو نُقل بأن يحتفظ بوسومه ونجمته وحالة أرشفته وملاحظاته بدلاً من أن يُعامَل كمستودع جديد تماماً. وهنا تكون الخسارة فورية لا مؤجَّلة: أي مستودع كان قد أُعيدت تسميته أو نُقل **قبل** فقدان الملف سيحصل على معرّف جديد تماماً في الفحص التالي مباشرة، وتبقى وسومه ونجمته وأرشفته وملاحظاته عالقة تحت المعرّف الذي لم يعد يحمله. أما المستودعات التي لم تُعَد تسميتها قطّ فلا تتأثر، ومن لحظة إعادة بناء السجلّ تصبح عمليات إعادة التسمية محميّة مرة أخرى.

يتجاوز `REPO_RADAR_CONFIG` و`REPO_RADAR_PORT` (الافتراضي 17420) مسار الإعدادات والمنفذ — اضبط **كليهما** لتشغيل نسخة ثانية مستقلة تماماً. يرتبط الخادم بـ `127.0.0.1` فقط ويتحقق من ترويسة Origin في كل طلب API وWebSocket.

المنفذ الافتراضي يقع فوق نطاق المنافذ الديناميكية للنظام عن قصد: يستخدم Windows النطاق 49152–65535 افتراضياً، لكنه يصبح 1024–15000 بعد تثبيت Hyper-V/WSL2، والنظام يحجز كتلاً كاملة من النطاق النشط — أي منفذ داخله يفشل في الارتباط بالخطأ `EACCES`، وهذه الكتل تتغيّر مع كل إعادة تشغيل.

إذا تعذّر الارتباط بالمنفذ **الافتراضي**، يتراجع repo-radar (`+1000` و`+2000` و`+3000`، ثم منفذ يخصصه النظام) بدل أن يرفض البدء، ويتذكّر المنفذ الذي استقر عليه ليعيد استخدامه في التشغيلات التالية، ويعرضه بجوار رقم الإصدار في ⚙ الإعدادات. إعادة استخدامه مهمة لأن المنفذ جزء من أصل (origin) الصفحة، واللوحة تحفظ العروض المخصصة وسجل النشاط والسمة واللغة في تخزين المتصفح المرتبط بالأصل — تركه يتنقّل ذهاباً وإياباً يجعل تلك البيانات تختفي وتعود. احذف `<مجلد الإعدادات>/port-state.json` للعودة إلى المنفذ الافتراضي.

المنفذ الذي تحدده بنفسك عبر `REPO_RADAR_PORT` لا يُستبدل أبداً — فهو التزام تجاه إشاراتك المرجعية ووكلائك العكسيين وسكربتاتك، لذا يفشل بوضوح إن تعذّر الارتباط به. والأمر نفسه في `npm run dev`، حيث يتحدد هدف وكيل vite عند تحميل الإعدادات.

## التطوير

```bash
npm run dev     # vite + نافذة التطبيق مع إعادة التحميل الساخن
npm test        # حِزم اختبار server + web + desktop وفحوص الأنواع
npm run dist    # بناء المثبِّتات في dist-electron/
```

المكدّس التقني: غلاف Electron + Node + Hono (كل وصول إلى git عبر `spawn`، بلا أي تبعيات أصلية native) + Vite / React 19 / antd 6، مع chokidar + WebSocket للتحديثات الحية. يعمل خادم Hono داخل العملية الرئيسية لـ Electron وتحمّله النافذة عبر `127.0.0.1`، فالواجهة مجرد HTTP + WebSocket عاديان — تماماً كما لو كانت في متصفح.
